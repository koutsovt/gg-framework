# Architecture Decision Records — ggquant

Seed ADRs capturing the foundational decisions made before the build started.
Going forward, `ggquant` emits `DecisionRecord` objects that `ggarch` stores;
these five are written by hand so the log has content from day one.

Format per record: Context · Decision · Consequences.

---

## ADR-0001 — `ggquant` is a new monorepo package, not a fork of `ggcoder`

**Context.** The instrument needs a home in the gg-framework monorepo. `ggcoder`
was considered as a base, but `ggcoder` is an LLM coding agent built around a
deliberately minimal system prompt; the instrument is deterministic numerical
code with a different purpose.

**Decision.** `ggquant` is a new package, sibling to `gg-ai`, `gg-agent`,
`ggarch`. It is not a fork of `ggcoder` and shares no agent runtime with it. It
inherits the monorepo's TypeScript setup and discriminated-union conventions.

**Consequences.** Clean separation of concerns. The instrument has no agent loop
and no system-prompt budget to manage. `ggcoder` may still be the *tool used to
build* `ggquant`, but it is not a dependency of it.

---

## ADR-0002 — The deterministic core has zero LLM dependency

**Context.** A trading-validation instrument could be built with LLM components
throughout. But the core value is reproducibility: the same setup and data must
yield the same verdict, every run, on any machine.

**Decision.** Pipeline Stages 01–04 (Definition Layer, Detector Registry,
Trajectory Simulator, Honesty Harness) are pure deterministic code with no model
calls and no `gg-ai` import. An optional LLM "philosophy-veto" layer may be
added much later; it is separable and explicitly out of scope for the core.

**Consequences.** Detectors, the simulator, and the harness are pure functions —
testable, cacheable, and reproducible. The honesty harness's verdict is
trustworthy because nothing stochastic sits in the path that produces it. This
decision also enables the performance strategy (ADR-0005).

---

## ADR-0003 — The Decision Log is `ggarch`; the instrument builds no logging system

**Context.** Pipeline Stage 05 needs to record every definitional choice,
parameter selection, and harness verdict. `ggarch` already exists as a
decision-quality / ADR tool in the monorepo.

**Decision.** `ggquant` does not build its own logging system. It emits typed
`DecisionRecord` objects; `ggarch` ingests, structures, and stores them. The
contract is one-directional: `ggquant` produces, `ggarch` consumes.

**Consequences.** Stage 05 is essentially free. More importantly, parameter
choices are captured *before* the backtest that tests them is run — the single
strongest guard against curve-fitting, since a number's rationale cannot be
retro-fitted after seeing it win. `ggarch` makes the honesty harness honest
about itself.

---

## ADR-0004 — TradingView is a cross-check and charting tool, not a data-of-record or validation environment

**Context.** TradingView is available and is a natural charting tool. The
temptation is to use it as a data source and to trust Pine Script strategy
backtests.

**Decision.** TradingView is used for two things only: (1) exploratory charting,
and (2) a *visual cross-check* — porting a detector's rule to a Pine indicator
and eyeballing whether it tags the same events the TypeScript detector emits.
TradingView is **not** the data-of-record (its exported history has gaps and
varies by feed; the data-of-record is a proper broker/exchange API) and **not**
the validation environment (Pine strategy backtests have no holdout, no random
baseline, no degrees-of-freedom audit, no Monte Carlo).

**Consequences.** TradingView is an external tool used alongside `ggquant`, not
a dependency. The verdict is issued only by the honesty harness. The Pine port
serves as a free second detector implementation for catching detector bugs
visually.

---

## ADR-0005 — Fast validation loop via caching and parallelism; never by thinning the harness

**Context.** "Make it fast" is a stated prerequisite. It could be read three
ways: fast to iterate, fast to run a full backtest, or fast at live-tick
latency. Only the first two apply — there is no live execution path (ADR
boundary with SPEC §0).

**Decision.** The performance target is a **sub-second validation loop** for an
incremental change to a setup. Achieved by:

- **Content-hash caching of the pure layers** — detectors, ATR, simulator.
  Changing one parameter reruns only the affected detector; data load and
  untouched layers are served from cache.
- **Worker-thread parallelism** for full backtest runs — each walk-forward
  fold, baseline shuffle, and Monte Carlo iteration is independent. Built
  correct single-threaded first, then parallelised.

Speed is **never** obtained by reducing validation. The honesty harness's four
tests are fixed; dropping the random baseline or shrinking the Monte Carlo
iteration count to speed a run is prohibited — that is the instrument lying
faster.

**Consequences.** The purity of the core (ADR-0002) is what makes content-hash
caching sound and parallelism safe. The iteration loop stays fast enough that
corners are never cut under time pressure, which protects the integrity of every
verdict.
